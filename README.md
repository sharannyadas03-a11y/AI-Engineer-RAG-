# Employee Policy RAG Assistant

A Retrieval-Augmented Generation assistant that answers employee questions about
expense, travel, finance, and HR handbook policy using only the provided documents,
with citations, follow-up support, and several bonus features.

> **Note on the source documents:** the assignment brief named four policy documents
> (Expense, Travel, Finance, Employee Handbook) but did not attach their actual content.
> I authored representative sample versions of all four (`/data/*.md`) so the pipeline
> could be built and demonstrated end-to-end. Swapping in the real company documents
> requires no code changes — just replace the files in `/data` (see Setup).

---

## 1. Setup Instructions

### Requirements
- Python 3.9+
- `pip install -r requirements.txt` (scikit-learn, numpy, requests, flask)

### Run the CLI (interactive chat)
```bash
cd rag_assistant
pip install -r requirements.txt
python app.py
```

### Ask a single question non-interactively
```bash
python app.py --ask "What is the meal expense limit for domestic travel?"
python app.py --ask "What is the mileage rate?" --filter "Finance Policy"   # metadata filter
python app.py --stream                                                      # streamed CLI chat
```

### Run the web UI
```bash
python web_app.py
# open http://localhost:5050
```

### Enable real LLM-generated answers
By default (no API key) the assistant runs in an **offline extractive mode** — see
Design Decisions below for why. To use a real LLM for generation, add a `.env`
file in `rag_assistant/` (already `.gitignore`d, never commit it):

```bash
# .env
OPENROUTER_API_KEY=sk-or-v1-...
OPENROUTER_MODEL=anthropic/claude-3.5-sonnet   # any model slug from openrouter.ai/models
```

`app.py` / `web_app.py` load `.env` automatically via `python-dotenv`. OpenRouter is
tried first (any model behind one key); if `OPENROUTER_API_KEY` isn't set, the code
falls back to a direct Anthropic call if `ANTHROPIC_API_KEY` is set instead:

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
python app.py
```

With a key set (either provider), every answer is generated by the LLM, grounded
strictly in the retrieved chunks, following the system prompt in `src/llm.py`. If the
LLM call fails for any reason (bad key, no network, rate limit), the app automatically
falls back to offline extractive mode rather than erroring out.

> **Security note:** never hardcode an API key directly into source files or commit
> a `.env` file to version control — anyone with the key can spend against your
> account. If a key is ever pasted somewhere it could be logged or shared (a chat
> message, a support ticket, a public repo), treat it as compromised and rotate it
> from the provider's dashboard.

### Using your real policy documents
Drop your own `.md` or `.txt` files into `/data` (one file per policy, using `##`
headers for sections — this drives both chunking and citation section names) and
re-run. No other setup is needed; the index is rebuilt from `/data` on every start.

## 2. Architecture Overview

```
 data/*.md
     │
     ▼
 chunker.py        → loads docs, splits by "## " section, further splits long
                      sections into overlapping sentence windows
     │
     ▼
 retriever.py       → HybridRetriever: BM25 (bm25.py) + TF-IDF cosine (sklearn),
                       min-max normalized and fused; query expansion; metadata
                       filtering by document; lightweight rerank by section-title
                       overlap; drops near-zero-relevance results
     │
     ▼
 conversation.py    → tracks turn history; rewrites short/pronoun follow-up
                       queries by folding in prior questions before retrieval
     │
     ▼
 llm.py             → builds a grounded prompt from retrieved chunks + history;
                       calls OpenRouter if OPENROUTER_API_KEY is set (any model),
                       else Anthropic directly if ANTHROPIC_API_KEY is set,
                       otherwise falls back to an offline extractive answer
                       built from the same retrieved chunks
     │
     ▼
 app.py / web_app.py → CLI and Flask front-ends over the same pipeline;
                        feedback.py logs 👍/👎 to a JSONL file
```

Everything is file-based and dependency-light: no vector database, no external
embedding API. Given the size of a typical company policy corpus (a handful of
documents, a few dozen KB each), an in-memory sparse index rebuilt on process
start is simpler to run, review, and deploy than a persistent vector DB, while
still meeting every functional requirement in the brief.

## 4. Design Decisions

- **Section-aware chunking, not fixed-size chunking.** Splitting on `##` headers
  first (falling back to overlapping sentence windows only for long sections)
  keeps each chunk to one coherent policy topic, which both improves retrieval
  precision and makes citations meaningful ("Section 8: Non-Reimbursable Items"
  vs. an arbitrary chunk number).
- **Hybrid BM25 + TF-IDF instead of dense embeddings.** This sandbox has no
  outbound network access, so a real embedding model (OpenAI/HF) couldn't be
  downloaded or called while building this. BM25+TF-IDF is a fully offline,
  legitimate substitute that performs well here because policy questions
  usually hinge on exact terms and numbers ("INR 10,000", "60 days"), where
  lexical retrieval is a strong signal. `HybridRetriever` is written as a clean
  seam — swapping in a dense embedding backend later only touches
  `retriever.py`.
- **A small custom stemmer**, shared by BM25 and TF-IDF, closes the gap between
  query/document word forms (e.g., "alcohol" vs. "alcoholic", "approve" vs.
  "approval") without pulling in an NLTK/spaCy download.
- **Pre-normalization relevance filtering.** Min-max score normalization always
  stretches the *best remaining* candidate toward 1.0 — even for a totally
  off-topic query — which would otherwise make the retriever look falsely
  confident. Chunks with literally zero raw lexical overlap are dropped before
  normalization, and results are dropped again if their fused score is
  ~0 after fusion, so an out-of-scope question correctly yields "not found"
  rather than a fabricated-sounding answer.
- **Pluggable, dual-mode generation.** `llm.py` calls the real Anthropic API
  when `ANTHROPIC_API_KEY` is set, using a strict system prompt that forbids
  outside knowledge and requires citations. When no key is present (this
  sandbox), it falls back to an offline extractive mode that selects the most
  query-relevant sentences from the same retrieved chunks — so the two modes
  are behaviorally consistent (same retrieval, same grounding, same
  citation format), and the whole pipeline is demonstrable without any API
  key or network access.
- **Lightweight follow-up handling instead of relying on the LLM alone.**
  Passing conversation history to the LLM helps with *generation* continuity,
  but does nothing for *retrieval* continuity — a short follow-up like "what
  about for a regular employee?" has almost no lexical signal on its own.
  `Conversation.rewrite_query_for_retrieval` detects short/pronoun-heavy
  follow-ups and folds in the prior question(s) before retrieval.

### Bonus features implemented
| Bonus item | Where |
|---|---|
| Hybrid Search | `retriever.py` — weighted BM25 + TF-IDF fusion |
| Metadata Filtering | `retriever.py` `doc_filter` param; CLI `:filter`, `--filter`; web UI dropdown |
| Query Expansion | `retriever.py` `QUERY_EXPANSIONS` domain synonym map |
| Reranking | `retriever.py` `_rerank` — section-title overlap boost |
| Incremental Indexing | `retriever.py` `add_documents(rebuild=False)` |
| Feedback mechanism | `feedback.py` + CLI `:feedback up/down` + web UI 👍/👎 |
| Streaming responses | `llm.py` `stream_answer`; CLI `--stream` |
| OCR for scanned PDFs | **Not implemented** — no scanned PDFs were in scope for this data set; see Improvements |

## 5. Assumptions

- The actual company policy documents weren't attached to the assignment, so
  representative sample policies were authored to build and demonstrate the
  system. Structure (markdown with `##` section headers) was chosen
  deliberately so real documents can be dropped in with the same shape.
- A single "employee" persona is assumed — no role-based access control or
  per-employee document visibility is implemented (e.g., a policy document
  restricted to managers only). This is called out explicitly as a gap since
  a real HR/Finance assistant would need it.
- Feedback and conversation state are kept in local files / in-memory
  per-process, appropriate for a single-user assignment demo, not a
  multi-tenant production deployment.

---

## 6. Trade-offs

- **Sparse (BM25/TF-IDF) retrieval vs. dense embeddings:** faster to build,
  zero external dependencies, fully offline-testable, but weaker on
  paraphrased questions with no shared vocabulary (mitigated partially by
  query expansion + stemming, not eliminated).
- **Rebuild-on-add incremental indexing vs. true delta indexing:** simpler
  and fast enough for a corpus of this size (rebuild is sub-second), but
  would not scale to a corpus of thousands of documents without moving to an
  incremental-friendly index structure.
- **Offline extractive fallback vs. requiring an API key:** guarantees the
  whole system is runnable and demonstrable with zero configuration, at the
  cost of noticeably lower answer quality/fluency than a real LLM call
  (sentence extraction vs. true synthesis across chunks).
- **No vector database:** an in-memory index rebuilt on startup is simpler to
  run and inspect for an assignment of this scope, but doesn't persist across
  restarts of a long-running service the way a vector DB with a REST API
  would in production.

---

## 7. Improvements With More Time

- Add a dense embedding backend (e.g., an actual embedding API, or a local
  sentence-transformers model) behind the same `HybridRetriever` interface,
  and combine it with BM25 for true hybrid dense+sparse search — this would
  meaningfully help with paraphrased/semantic queries that share little
  vocabulary with the source text.
- Add OCR (e.g., via `pytesseract` + `pdf2image`) for scanned PDF policy
  documents, per the bonus list.
- Add role-based metadata filtering (e.g., a document tagged "managers only")
  tied to an authenticated user identity.
- Move feedback and conversation history from local files/in-memory dicts to
  a real database, and build a small dashboard over the feedback log to spot
  systematically low-rated questions or chunks.
- Add automated retrieval-quality evaluation (a small labeled Q&A set with
  expected source sections, scored via recall@k) so future changes to
  chunking/retrieval can be regression-tested rather than checked by hand as
  was done here.
- Real cross-encoder reranking (currently a lightweight title-overlap
  heuristic) once a network-connected environment / model is available.
- Add response caching for repeated/common questions to reduce LLM cost and
  latency in the real-LLM mode.
